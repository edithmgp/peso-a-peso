# Documento Técnico v1 — Peso a Peso

## 0. Identificación del proyecto

**Nombre:** Peso a Peso
**Tipo:** Aplicación web responsive con enfoque mobile-first
**Propósito:** Asistente financiero inteligente para la economía doméstica
**Arquitectura:** Sistema multi-agente con orquestación cíclica
**Estado:** Diseño técnico para construcción del MVP

---

# 1. Visión del producto

*Peso a Peso* busca ayudar a personas y hogares a controlar sus gastos cotidianos, anticipar el comportamiento financiero del mes y tomar decisiones de gasto más conscientes.

El problema original está definido como el descontrol financiero doméstico producido, entre otras causas, por aumentos imprevistos de servicios, gastos pequeños acumulativos y falta de planificación de compras. La aplicación busca centralizar los consumos, analizar patrones, proyectar el gasto mensual y actuar como un coach financiero personalizado. 

La aplicación también será válida para personas cuya actividad económica se desarrolla desde el domicilio, como trabajadores independientes, freelancers y trabajadores home office, donde se mezclan determinados gastos del hogar con la actividad laboral.

### Objetivo del MVP

El MVP deberá permitir:

1. Registrar gastos manualmente.
2. Registrar un gasto mediante lenguaje natural.
3. Cargar una fotografía de un ticket.
4. Extraer información del comprobante mediante IA/OCR.
5. Solicitar confirmación humana antes de guardar el resultado.
6. Visualizar presupuesto y gastos.
7. Calcular dinero disponible por día.
8. Detectar consumos anómalos.
9. Proyectar el gasto al cierre del mes.
10. Generar recomendaciones personalizadas.
11. Registrar feedback del usuario sobre las recomendaciones.
12. Utilizar ese feedback para modificar progresivamente el comportamiento del sistema.

# 5. Arquitectura multi-agente

Los cinco agentes originales se mantienen porque forman parte importante de la propuesta conceptual.

La diferencia es que ahora definiremos explícitamente **qué reciben, qué producen y quién los ejecuta**.

## 5.1 Agente de Captura e Ingesta

### Responsabilidad

Transformar entradas del usuario en información financiera estructurada.

### Entradas

* texto;
* fotografía;
* datos manuales.

### Procesamiento IA

* extracción de comercio;
* monto;
* fecha;
* categoría;
* descripción.

### Salida

```text
ExpenseCandidate
```

Ejemplo:

```json
{
  "merchant": "Coto",
  "amount": 15230,
  "date": "2026-08-17",
  "category": "food",
  "description": "Compra supermercado",
  "confidence": 0.96
}
```

El campo `confidence` será importante para gestionar errores.

# 6. Agente Analizador de Patrones

Analiza el comportamiento financiero actual comparándolo con el histórico.

### Responsabilidades

* gasto acumulado;
* promedio diario;
* velocidad de consumo;
* gasto por categoría;
* comparación histórica;
* detección de gastos anormales;
* identificación de gastos hormiga.

### Entrada

```text
Expense
+
HistoricalFinancialData
```

### Salida

```text
FinancialAnalysis
```

Ejemplo:

```json
{
  "category": "food",
  "current_spend": 135000,
  "historical_average": 105000,
  "deviation_percentage": 28.57,
  "risk": "medium"
}
```

La primera entrega ya definía como parámetro una alerta cuando un gasto individual supera en más de 40% la desviación estándar histórica de la categoría. 

**Importante:** esta regla será calculada por código, no por el LLM.

# 7. Agente Planificador y Proyector

Es el componente responsable de responder:

> **¿Voy a llegar a fin de mes?**

Calcula:

* presupuesto restante;
* días restantes;
* disponible diario;
* gastos fijos pendientes;
* gasto proyectado;
* posible ahorro;
* riesgo de exceder presupuesto.

Ejemplo:

```text
Presupuesto:          $600.000
Gastado:              $420.000
Gastos fijos futuros: $60.000
Disponible real:      $120.000
Días restantes:             10

Disponible diario:
$12.000
```

La prioridad de gastos fijos se mantiene como regla de negocio, tal como estaba planteada originalmente.

# 8. Agente Evaluador y Generador de Alertas

Este agente funciona como **filtro crítico**.

No toda observación del Analizador debe convertirse automáticamente en una alerta.

Evalúa:

```text

   +

   +
Reglas
   +
Perfil del usuario

```

Posibles resultados:

```text

INFO

CRITICAL
```

Ejemplo:

> ⚠️ Tu gasto en comida está creciendo más rápido que tu presupuesto. Si mantenés este ritmo, podrías superar el límite mensual.

# 9. Meta-Agente de Aprendizaje Continuo

Esta es la pieza que vamos a profundizar respecto de la primera entrega.

No implementaremos inicialmente RL completo.

Usaremos un **modelo de aprendizaje incremental basado en feedback y scoring contextual**.

## Señales

El sistema registra:

* alerta enviada;
* categoría;
* momento;
* tono;
* si fue visualizada;
* feedback explícito;
* comportamiento posterior.

Por ejemplo:

```text
Alerta comida
→ Me sirvió

Alerta ocio
→ No me sirvió

Alerta comida
→ Me sirvió
```

El perfil puede evolucionar:

```text
food:
  positive_feedback = 8
  negative_feedback = 1

leisure:
  positive_feedback = 2
  negative_feedback = 7
```

El agente puede entonces:

* aumentar prioridad de determinadas alertas;
* reducir alertas poco útiles;
* modificar tono;
* anticipar recomendaciones.

### Arranque en frío

Para un usuario nuevo no existen datos históricos suficientes.

Por eso inicialmente utilizaremos:

```text
Reglas generales
+
Feedback explícito
+
Histórico disponible
```

A medida que aumenta el volumen de información, el comportamiento personalizado adquiere mayor peso.

Esto nos permite responder de manera concreta a la pregunta del docente sobre **cómo aprende el Meta-Agente y cómo se resuelve el cold start**.

# 10. Orquestación

Esta es probablemente la sección más importante del documento.

## ¿Cómo se comunican realmente los agentes?

No utilizaremos cinco agentes independientes conversando libremente entre sí.

Utilizaremos:

### **Orquestador central + estado compartido persistente**

El orquestador controla el ciclo.

```text
Usuario
   │
   ▼
Orquestador
   │
   ▼
Captura
   │
   ▼
Analizador
   │
   ▼
Planificador
   │
   ▼
Evaluador
   │
   ▼
Respuesta
   │
   ▼
Usuario
   │
   ▼
Feedback
   │
   ▼
Meta-Agente
   │
   ▼
Memoria
   │
   └──────────────► nuevo ciclo
```

Los agentes no necesitan conocerse directamente.

Cada agente:

1. recibe un estado;
2. ejecuta su responsabilidad;
3. devuelve un resultado;
4. el orquestador actualiza el estado;
5. decide qué agente ejecutar a continuación.

# 11. Estado compartido

Para evitar una arquitectura de módulos aislados, utilizaremos un objeto conceptual:

```text
AgentContext
```

Contendrá información como:

```json
{
  "user_id": "...",
  "current_month": "2026-08",
  "expense": {},
  "financial_analysis": {},
  "projection": {},
  "risk": {},
  "user_profile": {},
  "previous_alerts": [],
  "feedback": []
}
```

El orquestador va enriqueciendo este contexto durante el ciclo.

Esto nos permite explicar técnicamente la cooperación:

> Los agentes no se comunican mediante conversaciones libres; cooperan mediante un contexto estructurado administrado por el orquestador.

**Esta frase va a ser importante para la defensa oral.**

# 19. Métricas de éxito

**Error de proyección de cierre mensual**


### Alertas

**Tasa de aceptación**


**Tasa de corrección humana**

Cuántas extracciones necesitan ser corregidas.

### Uso

**Porcentaje de gastos registrados**

Frecuencia de uso del dashboard y respuesta a alertas.

La "tranquilidad mental" que mencionabas originalmente no se puede medir directamente en un MVP, pero podemos utilizar la **aceptación de alertas y reducción de desvíos presupuestarios como proxies**.

# 25. Decisiones que considero cerradas

A partir de ahora tomaría como **baseline oficial del proyecto**:

> **Peso a Peso = React/TypeScript + FastAPI/Python + Supabase/PostgreSQL + Gemini + orquestador propio + cinco agentes + memoria persistente + arquitectura OODA + deployment Vercel/Render.**

Y tres decisiones arquitectónicas son especialmente importantes:

### 1. No es un chatbot financiero

Es un **sistema agéntico de gestión financiera** que usa IA como componente.

### 2. No es un pipeline lineal

Es un **ciclo OODA con memoria y feedback**.

### 3. Los agentes no son cinco LLMs independientes

Son **componentes especializados coordinados por un orquestador central mediante un contexto estructurado**.

Eso nos da una historia técnica mucho más sólida para defender.
