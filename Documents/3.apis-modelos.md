# Documento Técnico v1.3 — Contrato API + Modelos Pydantic/TypeScript

**Objetivo:** definir exactamente qué entra y qué sale de cada endpoint, antes de escribir frontend y backend.

---

# 29. Principio API-first

El frontend y backend se desarrollarán contra contratos definidos.

```text
                    CONTRATO
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
        FastAPI              React/TS
        Pydantic              Types
```

Esto evita que Antigravity invente formatos diferentes en cada lado.

---

# 30. Versionado

Todos los endpoints comenzarán con:

```text
/api/v1/
```

Por ejemplo:

```text
/api/v1/expenses
```

Si en el futuro cambiamos radicalmente el contrato:

```text
/api/v2/
```

---

# 31. Convención HTTP

Usaremos:

| Acción              | Método    |
| ------------------- | --------- |
| Crear               | POST      |
| Consultar colección | GET       |
| Consultar elemento  | GET       |
| Modificar           | PUT/PATCH |
| Eliminar            | DELETE    |

---

# 32. Respuesta estándar

Las respuestas exitosas de recursos utilizarán directamente el objeto correspondiente.

Ejemplo:

```json
{
  "id": "...",
  "amount": 15000,
  "category": "food"
}
```

Los errores utilizarán el formato estándar de FastAPI.

No vamos a crear una envoltura artificial:

```json
{
  "success": true,
  "data": ...
}
```

salvo que posteriormente aparezca una necesidad concreta.

# 39. GET `/api/v1/expenses/{id}`

Devuelve un gasto individual.

Si no pertenece al usuario:

```text
404 Not Found
```

No debemos devolver:

```text
403 "ese gasto existe pero no puedes verlo"
```

porque eso podría permitir inferir información sobre otros usuarios.

---

# 40. PUT `/api/v1/expenses/{id}`

Permite corregir:

* monto;
* categoría;
* descripción;
* comercio;
* fecha.

No permitirá modificar:

```text
user_id
created_at
```

---

# 41. DELETE `/api/v1/expenses/{id}`

Elimina el gasto del usuario.

En el MVP utilizaremos eliminación física.

Podríamos implementar soft delete posteriormente si fuera necesario para auditoría.

# 53. Confirmación OCR

```text

```

### Request

```python
class ReceiptConfirm(BaseModel):
    candidate: ReceiptCandidate
    confirmed: bool
```

Si:

```text
confirmed = false
```

no se crea el gasto.

Si:

```text
confirmed = true
```

se crea el gasto y se dispara el ciclo de agentes.

# 62. Contrato Frontend ↔ Backend

La regla definitiva será:

> **El frontend consume los modelos definidos en este documento; no inventa estructuras propias.**

Idealmente, en una etapa posterior podemos generar automáticamente parte de los tipos TypeScript desde el OpenAPI de FastAPI, pero **para el MVP mantendremos explícitos los modelos TypeScript** para que el proyecto sea fácil de entender y defender.
