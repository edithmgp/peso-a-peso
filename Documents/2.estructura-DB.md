# Documento Técnico v1.2 — Diseño de Base de Datos

**Proyecto:** Peso a Peso
**Versión:** 1.2
**Motor:** PostgreSQL mediante Supabase
**Objetivo:** Definir el modelo físico de datos, relaciones, restricciones, índices, RLS y estrategia de migraciones del MVP.

---

## 1. Principios de diseño

La base de datos debe cumplir cinco objetivos:

1. **Integridad financiera:** los cálculos deben partir de datos consistentes.
2. **Aislamiento por usuario:** un usuario nunca debe poder consultar información de otro.
3. **Trazabilidad:** debemos poder reconstruir qué ocurrió durante un ciclo de agentes.
4. **Memoria:** debe conservar información histórica y de comportamiento.
5. **Evolución:** el esquema debe poder modificarse mediante migraciones versionadas.

La base de datos será relacional. Utilizaremos `UUID` como identificadores principales y `timestamptz` para fechas de auditoría.

# 3. Identificadores

Todas las tablas utilizarán:

```sql
id uuid primary key
```

generado mediante UUID.

### ¿Por qué UUID?

Porque:

* evita exponer identificadores secuenciales;
* funciona bien con aplicaciones distribuidas;
* permite generar IDs desde distintos componentes;
* es apropiado para Supabase/PostgreSQL.

---

# 4. Auditoría

Las tablas persistentes tendrán:

```sql
created_at timestamptz not null default now()
```

Las entidades que puedan modificarse tendrán además:

```sql
updated_at timestamptz not null default now()
```

No vamos a implementar inicialmente un sistema complejo de auditoría de cada modificación. `agent_events` cubrirá la trazabilidad específica del sistema agéntico.

# 5. `profiles`

La tabla representa la configuración financiera básica.

```sql
create table profiles (
    id uuid primary key references auth.users(id) on delete cascade,
    full_name text,
    currency text not null default 'ARS',
    monthly_income numeric(14,2),
    payday smallint,
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now(),

    constraint profiles_payday_check
        check (payday is null or payday between 1 and 31)
);
```

### Decisión importante

El `id` será exactamente el `id` del usuario de Supabase Auth.

Así obtenemos una relación:

```text
auth.users.id
       │
       ▼
profiles.id
```

---

# 6. `categories`

```sql
create table categories (
    id uuid primary key default gen_random_uuid(),
    name text not null unique,
    slug text not null unique,
    created_at timestamptz not null default now()
);
```

Datos iniciales:

```text
food
utilities
transport
leisure
housing
health
education
other
```

### ¿Por qué guardar `slug`?

Porque el código trabajará con valores estables:

```text
food
transport
housing
```

mientras que el nombre visible puede ser:

```text
Comida
Transporte
Vivienda
```

# 7. `budgets`

```sql
create table budgets (
    id uuid primary key default gen_random_uuid(),
    user_id uuid not null references profiles(id) on delete cascade,
    month date not null,
    amount numeric(14,2) not null,
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now(),

    constraint budgets_amount_check
        check (amount >= 0),

    constraint budgets_month_unique
        unique (user_id, month)
);
```

`month` representará siempre el primer día del mes.

Ejemplo:

```text
2026-08-01
```

Esto simplifica las consultas.

---

# 8. `expenses`

Es la tabla financiera central.

```sql
create table expenses (
    id uuid primary key default gen_random_uuid(),

    user_id uuid not null
        references profiles(id) on delete cascade,

    category_id uuid not null
        references categories(id),

    amount numeric(14,2) not null,

    description text,
    merchant text,

    expense_date date not null,

    source text not null default 'manual',

    confidence numeric(5,4),

    confirmed boolean not null default true,

    receipt_path text,

    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now(),

    constraint expenses_amount_check
        check (amount > 0),

    constraint expenses_source_check
        check (source in ('manual', 'text', 'ocr')),

    constraint expenses_confidence_check
        check (
            confidence is null
            or confidence between 0 and 1
        )
);
```

---

# 9. Estado de confirmación

Hay una pequeña decisión importante.

Para un gasto manual:

```text
confirmed = true
```

Para OCR:

```text
confirmed = false
```

hasta que el usuario confirme.

Por lo tanto:

```text
Foto
 ↓
Candidate
 ↓
expense
confirmed=false
 ↓
usuario confirma
 ↓
confirmed=true
```

Esto implementa directamente el mecanismo de seguridad que faltaba en la primera entrega.

# 10. `fixed_expenses`

```sql
create table fixed_expenses (
    id uuid primary key default gen_random_uuid(),

    user_id uuid not null
        references profiles(id) on delete cascade,

    category_id uuid not null
        references categories(id),

    name text not null,

    expected_amount numeric(14,2) not null,

    due_day smallint not null,

    priority text not null default 'normal',

    active boolean not null default true,

    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now(),

    constraint fixed_expenses_amount_check
        check (expected_amount >= 0),

    constraint fixed_expenses_due_day_check
        check (due_day between 1 and 31),

    constraint fixed_expenses_priority_check
        check (priority in ('low', 'normal', 'high'))
);
```

# 11. `alerts`

```sql
create table alerts (
    id uuid primary key default gen_random_uuid(),

    user_id uuid not null
        references profiles(id) on delete cascade,

    type text not null,

    severity text not null,

    title text not null,

    message text not null,

    category_id uuid references categories(id),

    agent_source text not null,

    created_at timestamptz not null default now(),

    seen_at timestamptz
);
```

Restricciones:

```sql
check (severity in ('info', 'warning', 'critical'))
```

y:

```sql
check (
    agent_source in (
        'capture',
        'analyzer',
        'planner',
        'evaluator',
        'meta_agent'
    )
)
```

---

# 12. `alert_feedback`

```sql
create table alert_feedback (
    id uuid primary key default gen_random_uuid(),

    alert_id uuid not null
        references alerts(id) on delete cascade,

    user_id uuid not null
        references profiles(id) on delete cascade,

    feedback text not null,

    created_at timestamptz not null default now(),

    constraint alert_feedback_value_check
        check (feedback in ('useful', 'not_useful'))
);
```

El `user_id` se conserva aunque pueda derivarse desde `alerts`, porque simplifica determinadas consultas y permite aplicar RLS directamente.

# 13. `behavior_profiles`

```sql
create table behavior_profiles (
    id uuid primary key default gen_random_uuid(),

    user_id uuid not null unique
        references profiles(id) on delete cascade,

    preferred_tone text not null default 'neutral',

    alert_frequency text not null default 'normal',

    category_scores jsonb not null default '{}'::jsonb,

    updated_at timestamptz not null default now(),

    constraint behavior_tone_check
        check (
            preferred_tone in (
                'neutral',
                'friendly',
                'direct'
            )
        ),

    constraint behavior_frequency_check
        check (
            alert_frequency in (
                'low',
                'normal',
                'high'
            )
        )
);
```

---

# 14. ¿Por qué `JSONB` para `category_scores`?

Porque durante el MVP todavía estamos explorando el modelo de aprendizaje.

Ejemplo:

```json
{
  "food": 0.82,
  "leisure": 0.31,
  "transport": 0.64
}
```

No tiene sentido crear ocho columnas independientes.

Si en una versión futura el modelo requiere análisis complejo, podemos normalizarlo.

# 15. `financial_snapshots`

```sql
create table financial_snapshots (
    id uuid primary key default gen_random_uuid(),

    user_id uuid not null
        references profiles(id) on delete cascade,

    snapshot_date date not null,

    total_budget numeric(14,2) not null,
    spent numeric(14,2) not null,
    remaining numeric(14,2) not null,

    available_per_day numeric(14,2) not null,

    projected_total numeric(14,2),

    risk_level text,

    created_at timestamptz not null default now(),

    constraint snapshot_risk_check
        check (
            risk_level is null
            or risk_level in (
                'low',
                'medium',
                'high'
            )
        )
);
```

# 16. `agent_events`

La tabla específica de observabilidad del sistema multi-agente.

```sql
create table agent_events (
    id uuid primary key default gen_random_uuid(),

    user_id uuid not null
        references profiles(id) on delete cascade,

    request_id uuid not null,

    agent_name text not null,

    event_type text not null,

    input_data jsonb,

    output_data jsonb,

    status text not null,

    duration_ms integer,

    created_at timestamptz not null default now(),

    constraint agent_name_check
        check (
            agent_name in (
                'capture',
                'analyzer',
                'planner',
                'evaluator',
                'meta_agent'
            )
        ),

    constraint agent_status_check
        check (
            status in (
                'started',
                'success',
                'failed'
            )
        )
);
```

# 17. `request_id`

Ejemplo:

```text
request_id = 8c7...
```

```text

 ├── capture
 ├── analyzer
 ├── planner
```

# 19. Índices

No vamos a llenar la base de índices innecesariamente.

Los primeros serán:

```sql
create index idx_expenses_user_date
on expenses(user_id, expense_date);

create index idx_expenses_user_category
on expenses(user_id, category_id);

create index idx_budgets_user_month
on budgets(user_id, month);

create index idx_alerts_user_created
on alerts(user_id, created_at desc);

create index idx_agent_events_request
on agent_events(request_id);

create index idx_agent_events_user_created
on agent_events(user_id, created_at desc);
```

Estos corresponden a las consultas más frecuentes previstas.

# 20. Row Level Security

Esta es una parte crítica del diseño.

Todas las tablas que contienen información del usuario tendrán:

```sql
alter table profiles enable row level security;
alter table budgets enable row level security;
alter table expenses enable row level security;
alter table fixed_expenses enable row level security;
alter table alerts enable row level security;
alter table alert_feedback enable row level security;
alter table behavior_profiles enable row level security;
alter table financial_snapshots enable row level security;
alter table agent_events enable row level security;
```

# 21. Regla fundamental de RLS

La regla general será:

```text
auth.uid() = user_id
```

Por ejemplo:

```sql
create policy "Users can view their own expenses"
on expenses
for select
using (auth.uid() = user_id);
```

Y:

```sql
create policy "Users can insert their own expenses"
on expenses
for insert
with check (auth.uid() = user_id);
```

El mismo principio se aplicará a las demás tablas.

---

# 22. Excepción: `profiles`

Como el `id` del perfil coincide con `auth.uid()`:

```sql
using (auth.uid() = id)
```

---

# 23. Categorías

Las categorías son datos compartidos.

Por lo tanto, los usuarios pueden:

```text
SELECT categories
```

pero el usuario final no podrá modificarlas durante el MVP.

---

# 24. Service Role

El backend utilizará las credenciales de servidor únicamente donde sea necesario.

La `SUPABASE_SERVICE_ROLE_KEY`:

* jamás estará en frontend;
* jamás se incluirá en GitHub;
* jamás se enviará al navegador.

# 25. Migraciones

La estructura se implementará mediante archivos:

```text

```

Ejemplo:

```text

002_rls_policies.sql
003_seed_categories.sql
```

Esto permite reproducir la base de datos.

# 27. Decisión sobre tickets

La imagen del ticket **no se almacenará directamente en PostgreSQL**.

Se guardará en:

```text
Supabase Storage
```

y `expenses.receipt_path` conservará la referencia.

```text
Storage
   │
   ▼
receipt_path
   │
   ▼
expense
```

Esto evita inflar la base de datos.
