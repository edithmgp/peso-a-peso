# Documento Técnico v1.1 — Contratos y estructura del proyecto

**Proyecto:** Peso a Peso
**Versión:** 1.1
**Objetivo:** Definir la estructura técnica concreta del MVP antes de iniciar la implementación en Antigravity.

---

## 1. Principio arquitectónico

El sistema estará compuesto por:

```text
                         USUARIO
                            │
                            ▼
                    ┌───────────────┐
                    │   FRONTEND    │
                    │ React/TS/Vite │
                    └───────┬───────┘
                            │ HTTPS
                            ▼
                    ┌───────────────┐
                    │    FASTAPI    │
                    │      API      │
                    └───────┬───────┘
                            │
                    ┌───────▼────────┐
                    │  ORQUESTADOR   │
                    │      OODA      │
                    └───────┬────────┘
                            │
          ┌─────────────────┼──────────────────┐
          │                 │                  │
          ▼                 ▼                  ▼
      CAPTURA          ANALIZADOR         PLANIFICADOR
          │                 │                  │
          └─────────────────┼──────────────────┘
                            ▼
                       EVALUADOR
                            │
                            ▼
                      META-AGENTE
                            │
                            ▼
                    ┌───────────────┐
                    │   SUPABASE    │
                    │ PostgreSQL    │
                    │ Auth + Storage│
                    └───────────────┘
```

El **orquestador** será el responsable de coordinar los agentes. Los agentes no tendrán conocimiento directo de otros agentes.

Esto soluciona específicamente la observación de la primera evaluación donde se señalaba que estaba pendiente definir el mecanismo real de cooperación.

# 26. Reglas financieras

Las reglas críticas estarán en Python.

Nunca dependerán de una respuesta del LLM.

## Regla 1 — Presupuesto

```text
gasto_total <= presupuesto
```

## Regla 2 — Gastos fijos

Los gastos fijos prioritarios se descuentan antes de calcular dinero libre.

## Regla 3 — Disponible diario

```text
disponible_diario =
presupuesto_realmente_disponible /
días_restantes
```

## Regla 4 — Anomalía

Se conserva el parámetro definido en la primera entrega:

> alerta cuando un gasto individual supere el umbral establecido respecto de la desviación estándar histórica de su categoría. 

Durante la implementación vamos a precisar matemáticamente el criterio para evitar ambigüedad.

## Regla 5 — No recomendar gasto por encima del dinero disponible

El sistema jamás generará una recomendación que implique superar el saldo disponible, respetando la restricción conceptual original.

# 28. Guardrail fundamental del LLM

El LLM **no decide directamente**:

* cuánto dinero tiene el usuario;
* cuánto gastó;
* cuánto queda;
* si puede gastar determinado monto.

Esos datos provienen de la base y de cálculos deterministas.

El LLM recibe los resultados ya calculados y se utiliza para:

> interpretar, explicar y personalizar.

Esto reduce considerablemente el riesgo de alucinaciones financieras.

## Una decisión importante antes de abrir Antigravity

Hay **un punto que deliberadamente no quiero cerrar todavía**: el detalle exacto del esquema SQL y las relaciones/constraints.

Ahora tenemos el modelo conceptual, pero antes de generar código conviene hacer el **v1.2 — Diseño de Base de Datos**, donde vamos a definir:

* SQL real;
* PK/FK;
* `UUID`;
* enums;
* índices;
* `NOT NULL`;
* `CHECK`;
* timestamps;
* relaciones;
* políticas RLS;
* estructura de `JSONB`;
* datos iniciales;
* estrategia de migraciones.

Después hacemos el **v1.3 — Contrato API + modelos Pydantic/TypeScript**, y recién ahí le damos a Antigravity la primera tarea.

Ese orden es deliberado: **primero datos → después contratos → después código**. Así evitamos que el agente de desarrollo invente estructuras mientras programa.
